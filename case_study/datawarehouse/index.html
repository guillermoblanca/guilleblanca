ETL Process: From Multiple Sources to Single Source of Truth

The core challenge: you don't trust a single data source. Google Analytics, Google Search Console, CRM systems, and ad platforms each report slightly different numbers. Why? Consent mode limitations, API differences, timing, and definitions diverge.

This pipeline solves that by automating extraction, normalization, reconciliation, and quality checks.

Phase 1
Extraction
Fetch raw data from GA4, GSC, CRM, and third-party APIs. Data lands in per-client staging tables.
Phase 2
Normalization & Cleansing
Clean, standardize formats, deduplicate, validate data types. Apply consistent naming conventions.
Phase 3
Reconciliation & Truth Building
Compare metrics across sources, investigate discrepancies, build unified tables (single source of truth).
Phase 4
Quality Scoring & Alerts
Daily automated quality tests, scoring, anomaly detection, and real-time alerting on data failures.
Phase 5
Production Data Warehouse
Store clean, validated data in PostgreSQL with full historical retention. Ready for analytics, BI, and ML.

Why Sources Disagree: The Discrepancy Landscape

The Problem
Google Analytics and Google Search Console report different metrics for the same event. Your CRM counts conversions differently than GA. Why? It's not a bug—it's the architecture of each system.
Source Why Data Differs Impact Solution
GA4 Event sampling, cookie consent mode, 16-month retention limit Sessions don't match CRM, old data discarded Store events directly, unlimited retention
GSC Filters, different session definition from GA4 Traffic numbers diverge from GA4 Reconcile GSC metrics against GA4
CRM Manual entry delays, custom conversion logic, offline events Doesn't match GA4 timing or definitions Map conversion windows, flag timing lags
Consent Reduces tracked events below actual traffic Traffic appears 10–50% lower than reality Track server-side, estimate true traffic

The warehouse normalizes these differences, documents them, and builds unified metrics you can trust.

Architecture & Technology Stack

Built for reliability, scalability, and ease of iteration.

Python 3.10+ PostgreSQL 14+ Docker FastAPI Pandas SQLAlchemy

Design Principles

  • Separation of Concerns: Extract → Normalize → Reconcile → Validate → Load, each as independent, testable units.
  • Idempotency: Any job can be re-run without corrupting data. Upserts, not appends.
  • Observability: Every step logs success/failure, row counts, processing time, and data quality metrics.
  • Extensibility: New sources plug in with minimal code. New quality checks are configuration-driven.

Why This Stack?

Component Reason
Python Rich ecosystem: pandas, SQLAlchemy, requests. Easy iteration, cloud-agnostic.
PostgreSQL Mature, open-source, ACID-compliant. Handles complex queries, full data retention. No vendor lock-in.
Docker Containerizes jobs for reproducible, consistent execution. CI/CD-ready.
FastAPI Async Python for real-time queries, webhooks, and dashboards. Type-safe, self-documenting.

Why a Data Warehouse? Beyond Native Tools

Unlimited Historical Data
GA4 limits history to 16 months. DW keeps everything. Enables YoY analysis, cohort studies, and ML on years of data.
Single Source of Truth
Reconcile GA4, GSC, CRM, and consent data into unified, auditable metrics. No more 'which number is right?'
Automated Data Quality
Real-time alerts on data failures. Catch bad data before it corrupts dashboards and decisions.
Ready for ML & Prediction
Clean historical data enables ML pipelines, predictive models, and advanced analytics native tools can't support.
Real-time Query Access
Custom API endpoints for real-time dashboards, mobile apps, and third-party integrations.
Multi-tenant Isolation
Single pipeline, multiple tenants with complete isolation. Unified orchestration reduces operational overhead.

Experience: From Design to Production

This project required expertise across the full data engineering lifecycle:

  • API Integration: OAuth flows, rate limiting, parsing diverse schemas from GA4, GSC, CRM systems.
  • ETL Architecture: Modular extraction, normalization, reconciliation, and loading stages—each independently scalable and testable.
  • Data Modeling: Multi-client schemas, normalized fact/dimension tables, optimized for analytics queries.
  • Quality Assurance: Automated testing, anomaly detection, alerting, and continuous monitoring.
  • Production Operations: Docker, logging, error recovery, and 24/7 monitoring for production reliability.
  • Stakeholder Communication: Documenting discrepancies, explaining trade-offs, and aligning solutions with business goals.

These Principles Apply Everywhere

This case study uses marketing data as an example (GA, GSC, CRMs). But the architecture, ETL patterns, and quality approach work across any industry:

E-commerce
Sales system + inventory management + customer data + marketing spend. Same ETL patterns, same data quality challenges.
SaaS / Subscription
Product analytics + billing system + customer support + revenue data. Same consolidation, same governance, different domain.
Operations / Logistics
Warehouse system + supplier data + shipping system + cost accounting. Same architecture, same data quality issues, same solution.

The domain changes. The data problems stay the same.

Key Takeaway

Data fragmentation is expensive. A well-designed ETL pipeline consolidates messy multi-source data into a reliable, auditable single source of truth—at enterprise scale.

The investment: clean architecture, automated QA, intelligent alerting. The return: trustworthy data, reduced risk, ML-ready platform.
